# LED-List — ТЗ для повторной генерации приложения

> Это самодостаточный промпт. Вставьте его целиком в новый чат с формулировкой:
> **«Сгенерируй это веб-приложение согласно ТЗ ниже. Начни с проектирования схемы БД и движка ёмкости петли, затем API и CRUD, затем UI. Localhost, демо-данные при первом запуске.»**

---

## 1. Что это

Мультитенантный **SaaS для оператора цифровой наружной рекламы (DOOH)** — управление сетью **LED-экранов**. Аналог системы для билбордов, но переработанный под цифровые экраны: рекламное место продаётся **не как «сторона конструкции на месяц»**, а как **слот в петле ротации** (плейлисте): доля показов с заданной длительностью ролика, количеством выходов и периодом трансляции.

Интерфейс на **русском**, валюта **₽**, формат дат **ДД.ММ.ГГГГ**.

## 2. Ключевое отличие от билбордов (обязательно)

1. Нет печати баннера, монтажа, подсветки. Вместо загрузки макета — загрузка **видео/креатива** (mp4, jpg, png, gif) с чтением разрешения и длительности.
2. Один экран показывает **много рекламодателей одновременно** через петлю. Продаётся **слот в петле**: длительность ролика (сек), выходов в сутки, период дат (от/до), тайм-слот (часть суток).
3. **Ёмкость петли**: в любой день сумма длительностей активных роликов на экране не может превышать длину петли (`loop_duration_sec`). Нельзя продать больше, чем вмещает петля.
4. Технические характеристики экрана вместо «формата 6х3»: физический размер (м), разрешение (px), шаг пикселя (P4/P6/P10), яркость (нит), тип (уличный/внутренний), ориентация, длина петли (сек), часы работы.
5. Занятость показывается **не «месяц занят одним клиентом», а как загрузка петли в %** по датам/месяцам.
6. Дополнительно: у экрана есть текстовое поле **«Сторона»** (А/Б — для двусторонних конструкций; у односторонних просто «А»).

## 3. Технологический стек

- **Frontend:** React 18 + TypeScript + Vite, react-router-dom, обычный CSS-файл (без UI-библиотек). Прокси `/api` → бэкенд.
  - Важно для Windows: в `vite.config.ts` указать `server.host: '127.0.0.1'`, `strictPort: true`, прокси на `http://127.0.0.1:3001` (иначе Vite может слушать только IPv6 ::1 и localhost будет недоступен).
- **Backend:** Node + Express + TypeScript (запуск через `tsx`), БД **SQLite** через `better-sqlite3` (схема переносима на PostgreSQL: целочисленные PK, FK, CHECK-ограничения). Пароли — `scrypt` (соль:хеш). Аутентификация — **JWT** (`jsonwebtoken`), срок 12 ч. Загрузка файлов — `multer` на диск в `data/uploads/`.
- **Мультитенантность:** во всех бизнес-таблицах поле `tenant_id`; каждый запрос фильтруется по тенанту из JWT.
- Порты: API **3001**, клиент **5173**. Запуск: `npm run dev` в `server/` и `client/`.
- БД-файл `server/data/led.db` создаётся и наполняется демо-данными при первом старте.

## 4. Роли и доступ

- `superadmin` — владелец платформы: раздел «Подписки» (тенанты). Не привязан к тенанту.
- `admin` — администратор компании: всё в рамках своего тенанта, включая справочники и создание/редактирование/удаление экранов.
- `manager` — менеджер по продажам: продажи и контрагенты; **запрещено** создавать/править/удалять экраны, удалять платежи, видеть подписки.

**discounts** — id, tenant_id, name, percent.
**tax_regimes** — id, tenant_id, name, rate (ставка сверху, %).
**owners** — id, tenant_id, name, phone, email, comment (владельцы конструкций).
**clients** — id, tenant_id, name, phone, email, address, contacts (JSON-массив контактных лиц), comment.
**managers** — id, tenant_id, user_id (nullable), name, phone, email.

**screens (LED-экран)** — id, tenant_id, code (напр. `GRZLED04001`), name, **side** (текст, А/Б), address, city_id, lat, lng, width_m, height_m, res_w, res_h, pixel_pitch, brightness, screen_type_id, orientation (horizontal|vertical), **loop_duration_sec** (длина петли, по умолч. 60), work_from, work_to, price_per_play, price_per_sec, tax_regime_id, owner_id, status (active|maintenance|inactive), tags, comment.

**campaigns (кампания/заказ)** — id, tenant_id, number (напр. `2026-041`), client_id, manager_id, created_at, status (draft|reserved|sold|cancelled), reserve_until (nullable), discount_id, discount_percent, production_cost (производство ролика — отдельная услуга вместо монтажа/печати), comment.

**ad_slots (слот размещения)** — id, tenant_id, campaign_id, screen_id, creative_id (nullable), duration_sec, date_from, date_to, plays_per_day, time_slot_id (nullable), price.

**payments** — id, tenant_id, campaign_id, pay_date, amount, method (bank|cash|card), comment.

**company_settings** — tenant_id (PK), legal_name, inn, address, phone, email, reserve_days (по умолч. 3), columns_config (JSON).

## 6. Ключевая бизнес-логика (движок — самое важное)

### 6.1 Движок ёмкости петли
Модель посуточная. Активными считаются слоты кампаний в статусе `reserved` или `sold`. Для экрана и диапазона дат для каждого дня: `used_sec = Σ duration_sec активных слотов, покрывающих этот день`; `load_pct = used_sec / loop_duration_sec * 100`. Функции:
- `loopLoad(screenId, from, to)` → по дням `{date, used_sec, load_pct}` + `max_load_pct`, `avg_load_pct`, `free_sec`.
- `checkCapacity(screenId, from, to, durationSec)` → влезает ли ролik: для каждого дня `used_sec + durationSec ≤ loop_duration_sec`; иначе `{ok:false, reason}` с перечнем дней переполнения.
- `checkCampaignCapacity(campaignId)` — **агрегатная** проверка перед бронью/продажей: по каждому экрану и дню сумма роликов ЭТОЙ кампании + чужих активных ≤ петля. (Важно: по-слотовая проверка пропускает переполнение собственными роликами кампании — нужна именно агрегатная.)
- `expireReservations()` — снимает просроченные брони (`status='reserved' AND reserve_until < today`) в `cancelled`, освобождая ёмкость. Вызывается в начале GET-хэндлеров списков/расписания.

### 6.2 Калькулятор стоимости
`perSec = price_per_sec > 0 ? price_per_sec : price_per_play / 5`
`base = perSec × duration_sec × plays_per_day × кол-во_дней_периода`
`× коэффициент тайм-слота (price_coef)` `× (1 − скидка%/100)` = net;
`налог = net × tax_rate/100` (сверху, для режимов с НДС); `total = net + налог`.
Итог разбивается на «Размещение» и опционально «Производство ролика».

### 6.3 Статусы кампании (переходы валидируются на сервере)
`draft → reserved | cancelled`; `reserved → sold | draft | cancelled`; `sold → cancelled`; `cancelled → draft`.
При переходе в `reserved`/`sold` — агрегатная проверка ёмкости, при переполнении **HTTP 409**. При `reserved` выставляется `reserve_until = today + reserve_days` (из настроек). Отмена освобождает петлю.

## 8. Разделы и навигация (админ-панель, верхнее меню с выпадающими списками)

- **Инвентарь экранов** — таблица с фильтрами. Настраиваемые колонки (чекбоксы, сохранять в localStorage). **Модальный фильтр с несколькими условиями** (поле: код, название/адрес, сторона, город, тип, шаг пикселя, владелец, статус, теги, загрузка ≥/≤, яркость; оператор: содержит/=/≥/≤; можно добавлять несколько условий, чипы применённых фильтров). Колонка **«Загрузка петли»** — индикатор-бар в % (зелёный <70, оранжевый <95, красный ≥95). Колонка **«Сторона»**. Селектор периода для расчёта загрузки.
  - Стиль строк инвентаря: отдельные «плашки» (border-spacing между строками), ячейки по центру, вертикальные разделители, скруглённые углы, код — моноширинный.
  - Кнопки в строке: «Плейлист» (ротация по дням) и «Изменить» (admin).
  - **Форма экрана** — многошаговая по секциям: Характеристики (код, название, **сторона**, тип, ориентация, статус) / Адрес и координаты / Технические параметры (размер, разрешение, шаг, яркость, длина петли, часы) / Финансы (₽/сек, ₽/выход, налог) / Владелец и доп. (владелец, теги, комментарий).
- **Продажи ▾**: Заказы/Кампании, Брони/Резервы, Платежи.
  - **Кампания (карточка)** — вкладки **Размещение / Креативы / Оплата**; кнопки смены статуса; сводные карточки (клиент, менеджер, размещение, производство, итого, оплачено).
  - **Добавление слота** — модалка с выбором экрана, длительности, выходов/сутки, периода, тайм-слота, ролика; **живая проверка ёмкости** и **калькулятор** с разбивкой цены; кнопка блокируется при переполнении активной кампании.
- **Контрагенты ▾**: Клиенты, Менеджеры, Владельцы экранов (CRUD).
- **Платежи** — реестр, суммы; платёж проводится из карточки кампании.
- **Настройки** (admin) — вкладки: Данные о компании (+ срок брони), Города/области, Типы экранов, Тайм-слоты (с коэф.), Скидки, Налоговые режимы.
- **Подписки** (superadmin) — тенанты: название, ИНН, даты регистрации/истечения, блокировка, создание тенанта с админом.

## 9. Окно занятости экрана (открывается по клику на название экрана в инвентаре) — ВАЖНАЯ ФИЧА

Модальное окно, вид «сетка занятости, как у билбордов, но по петле»:

1. **Шапка экрана** — плашка из 4 сегментов через разделители: `г. {город} | {адрес} | {сторона} | {код}`.
2. **Сетка занятости по месяцам** — строки = клиенты (сгруппированы по client_id из активных слотов года), столбцы = 12 месяцев (янв…дек). У каждого клиента синяя полоса, растянутая от месяца начала до месяца конца слота (клип по границам года). Клик по полосе открывает карточку кампании. В левом верхнем углу сетки — кнопка **«+»**.
3. **Кнопка «+»** открывает окно **«Добавить клиента на экран»**: выбор клиента, длительность ролика, выходов/сутки, период, тайм-слот; живая проверка ёмкости петли и расчёт стоимости; по подтверждению → `POST /screens/:id/book` (создаёт кампанию-бронь + слот), сетка обновляется.
4. **Полоса загруженности за выбранный месяц** (под сеткой): **месяцы в сетке кликабельны** — по клику на месяц полоса показывает загрузку экрана **именно за этот месяц**. По умолчанию выбран текущий месяц; выбранный месяц подсвечивается, его колонка выделяется. Полоса: заголовок «Загрузка экрана — {месяц} {год}», процент заполнения петли, сегменты по клиентам (ширина = duration_sec/loop), подпись «занято X сек» / «свободно N / loop сек». Если в месяце нет размещений — «Петля свободна».
   - Расчёт за месяц считается **на клиенте** из `slots`: перебрать дни месяца, найти пиковый день (макс. суммарная занятость), сегменты сгруппировать по клиентам.
5. Внизу — переключатель года (‹ пред · {год} · след ›).

## 11. Порядок реализации

1. Схема БД + сид + движок ёмкости петли (`loopLoad`, `checkCapacity`, `checkCampaignCapacity`, `calcPrice`, `expireReservations`).
2. Auth (JWT, роли, tenant-скоуп) + CRUD справочников и экранов.
3. Таблица инвентаря с фильтрами, настраиваемыми колонками, индикатором загрузки.
4. Кампании: карточка с вкладками, добавление слота с проверкой ёмкости и калькулятором, статусы, платежи, креативы.
5. Окно занятости экрана (шапка + месячная сетка + «+» бронирование + полоса загрузки по клику на месяц).
6. Подписки (superadmin), настройки компании.

## 12. Критерии приёмки

- Нельзя забронировать/продать при переполнении петли (в т.ч. собственными роликами кампании) — 409 с внятным сообщением; отмена освобождает ёмкость; просроченные брони снимаются автоматически.
- Калькулятор корректно учитывает секунды × выходы × дни × коэф. тайм-слота − скидка (+НДС сверху).
- Мультитенантность: менеджер не видит чужой тенант; менеджеру запрещены операции с экранами и удаление платежей.
- Клик по названию экрана открывает окно занятости; клик по месяцу меняет полосу загрузки на этот месяц; «+» бронирует клиента и обновляет сетку.
- Русский UI, ₽, даты ДД.ММ.ГГГГ.
